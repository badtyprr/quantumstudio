## Reproduce the include gap

Generate `oracle.qasm` using `bv.generate_oracle("111")` in the external
environment, then import this program with the dependency beside it:

```qasm
OPENQASM 3.0;
include "oracle.qasm";
qubit[3] q;
qubit[1] ancilla;
oracle(q, ancilla);
```

Expected: three controlled-X operations from data wires 0, 1 and 2 to ancilla
wire 3. Actual: importer exits with an error restricting includes to
`stdgates.inc` and `qelib1.inc`. Explicitly inlining the generated declaration
imports those three operations successfully.

Similarly, `bv.save_to_qasm("011")` generates `bernvaz.qasm`. Calling
`bernvaz(q, ancilla)` through an include fails; inlining imports ten operations.
These probes establish an include-resolution gap, not a general failure of
subroutine-local values or compile-time wire indices.

The observations above describe the original `92f80696` audit. Subsequent
implementation evidence is recorded below. Keep the source checklist unchecked
until the remaining cells, documented execution route and persistence behavior
are tested.

## Follow-up: local includes and classical subroutine storage

Rechecked on 2026-10-20 against the published `52875710` compiler and the unchanged
repository fixtures in `windows/fixtures/qb004/`. Local includes now resolve with
the explicit `--module-headers` option. Source/frozen CLI tests in
`windows/test-qasm-file-import.py` compare both generated subroutines with
explicitly inlined circuit documents. These are recurring scoped tests; they do
not execute the entire notebook.

The numerical route imports `oracle.qasm` as three operations and `bernvaz.qasm`
as ten. PR #307 adds numerical-composer source persistence and standalone export
checks, released in REL-06 (`22e4dca9`). The REL-05 classical route tested
here remains blocked on DEV-08:

```text
qasm-import.exe --source-file main.qasm --module-headers --classical
Integer declarations in subroutines require activation storage not yet supported.
```

This failure occurs for both original fixtures, using the wrapper shown above
with the matching include and subroutine name. It is a subroutine-storage gap,
not an include-resolution failure. Preserve the original local `s`, `n` and loop
variables when implementing and testing the fix. In this published build,
classical GUI persistence, standalone export and numerical equivalence for
these subroutines remain unverified because compilation fails before import.
